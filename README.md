# Movie Memory

Sign in with Google, tell us your favorite movie once, and get a fun fact about
it on every visit, generated by OpenAI and streamed to the page as it's written.

**Stack:** TypeScript · Next.js 16 (App Router) · React 19 · Tailwind CSS v4 ·
PostgreSQL · Prisma 7 · Auth.js v5 (Google) · OpenAI Responses API · Vitest

---

## Variant chosen: **A, Backend-Focused (Caching & Correctness)**

**Why A:** The interesting risks in this app are on the server. Every fact
costs an OpenAI call and a database write, and the obvious implementation
gets three things wrong:

- **Cost:** a refresh, a second tab, or a double-click each pay for another
  generation.
- **Concurrency:** parallel requests race to create duplicate facts.
- **Failure:** when OpenAI is slow or down, the user sees an error even
  though perfectly good facts are already stored.

Variant A addresses exactly these. The frontend was already in good shape
(streaming, loading states), so the remaining value was in making the backend
correct, cheap and testable. How each requirement is met is described in
[Variant A design](#variant-a-design).

---

## Features

- **Landing page** (`/`) with "Sign in with Google". Signed-in users are
  redirected automatically.
- **Google sign-in.** First-time users go to `/onboarding`, returning users to
  `/dashboard`.
- **Onboarding (first time only):** favorite movie, validated on the server
  (trimmed, whitespace collapsed, 1–200 characters) and saved with a
  conditional update, so it can only ever be set once, even from two devices.
- **Dashboard:** Google name, email and photo, the favorite movie, a logout
  button, and a fun fact that **streams in token by token**.
- **Route protection:** `/dashboard` and `/onboarding` redirect logged-out
  users to `/`. Every server action and API route re-checks the session itself.

### Data model

```
users                                        movie_facts
─────────────────────────────────────        ──────────────────────────────────────
id                          text PK          id          text PK
google_id                   text UNIQUE  ◄── user_id     text FK → users.id (ON DELETE CASCADE)
name, email, image          text?            movie       varchar(200)   title snapshot
favorite_movie              varchar(200)?    content     text
fact_generation_started_at  timestamptz?     model       text           e.g. gpt-5.4-mini
created_at, updated_at      timestamptz      created_at  timestamptz
                                             INDEX (user_id, movie, created_at DESC)
```

Design decisions:

- **Two tables, no Auth.js adapter tables.** Sessions are encrypted JWT
  cookies, so there are no `account` / `session` / `verification_token`
  tables. Users are identified by Google's permanent `sub` (`google_id`), not
  by email, which can change. The trade-off: logout is per device, and a
  stolen cookie stays valid until it expires (30 days).
- **`favorite_movie IS NULL` means "not onboarded".** That avoids a separate
  flag that could disagree with the data.
- **`movie_facts.movie` keeps a copy of the title,** so a fact always records
  which movie it was about. The cache and fallback match on
  `(user_id, movie)`, and the composite index serves both lookups with one
  index scan.
- **`timestamptz` everywhere.** The cache window and lease compare
  timestamps, so they must be real points in time.
  `src/lib/db.ts` pins database sessions to UTC, because Prisma sends dates
  as offset-less UTC text. Under a non-UTC server time zone, rows were landing
  hours in the future. A regression test covers this.
- **snake_case names in code and database alike** (no `@map`), so code, SQL
  and pgAdmin use the same names.

## Variant A design

All of the logic lives in [`src/lib/facts.ts`](src/lib/facts.ts)
(`factEvents()`). `POST /api/fact` resolves the user from the session and
streams the events as newline-delimited JSON:

```jsonc
{"type":"delta","text":"The T. rex roar "}     // 0..n: a new fact being generated
{"type":"fact","source":"new","content":"…","created_at":"…"}
//    source: "new" | "cache" | "shared" | "fallback"
{"type":"error","message":"Couldn't generate a fun fact right now…"}   // instead of "fact"
```

### Request flow

```
POST /api/fact
 │
 ├─ 401 not signed in / 409 not onboarded
 │
 ├─ 1. latest fact for (user, movie) younger than 60s? ── yes ─► source "cache"
 │
 ├─ 2. claim lease (one atomic UPDATE)
 │     ├─ lost: another request is generating ──► wait for its fact ─► source "shared"
 │     │                                          (it failed? → fallback)
 │     └─ won:
 │          ├─ re-check the cache (it may have been filled meanwhile) ─► "cache"
 │          ├─ stream from OpenAI (25s deadline) ─► deltas … ─► store ─► source "new"
 │          ├─ OpenAI fails/times out ─► latest stored fact ─► "fallback" | friendly error
 │          └─ finally: release lease
```

### 1. The 60-second cache window

- If the most recent fact for this **user + movie** is **less than 60 s old**,
  it's returned and OpenAI isn't called.
- Otherwise a new fact is generated, stored and returned.
- The comparison runs in SQL against the **database clock**
  (`created_at > now() - 60s`). All app servers then agree on fact age,
  whatever their own clocks say.
- The UI matches: the "Another fact" button shows `New fact in Ns` and stays
  disabled until the window ends, rather than offering a click that would
  return the cached fact.

### 2. Burst / idempotency protection: "generation in progress" lease

The approach is the **"generation in progress" flag** from the brief,
implemented as a lease, `users.fact_generation_started_at`:

```sql
UPDATE users
SET fact_generation_started_at = now()
WHERE id = $1
  AND (fact_generation_started_at IS NULL
       OR fact_generation_started_at < now() - interval '45 seconds')
RETURNING fact_generation_started_at
```

**Why this is race-free:**
- It's a single statement.
- Postgres row-locks the user while updating, and a concurrent `UPDATE` waits
  for that lock and then **re-checks the `WHERE` clause** against the
  committed row.
- So of N simultaneous requests (fast refreshes, multiple tabs, a
  double-click), exactly one gets a row back and calls OpenAI.

**What the losing requests do:** they poll every 400 ms for the winner's
fact and return it (`shared`). Every tab shows the same new fact, and the
user pays for one generation.

**Edge cases handled:**
- **Double-checked cache:** after winning the lease, the cache is checked
  again. A request that read "no fresh fact" just before another request
  stored one would otherwise generate a duplicate.
- **Crash safety:** the lease expires after **45 s**, longer than the 25 s
  generation deadline, so a crashed or killed process can't block a user
  forever.
- **Releasing only our own lease:** the release is conditional on the
  timestamp we wrote (`WHERE fact_generation_started_at = <our token>`), so a
  slow request never clears a newer request's lease.
- **Disconnects:** if the client disconnects, the OpenAI request is aborted,
  nothing is stored, and the lease is released (`finally`). The stream also
  checks for cancellation after every chunk.
- **Per user:** one user's lease never blocks another user.

**Alternatives considered:**

| Approach | Why not |
|---|---|
| In-memory lock (`Map<userId, Promise>`) | Breaks with more than one server instance or serverless; lost on restart |
| `pg_advisory_xact_lock` in a transaction | Holds a pooled DB connection open for the whole OpenAI stream (2–25 s) per user |
| Unique constraint on a 60 s bucket | Fixed buckets (`floor(epoch/60)`) don't match "less than 60 s old": two facts 2 s apart can land in different buckets |

### 3. Failure handling

- **OpenAI errors** (HTTP error, rate limit, no credits, `failed` /
  `incomplete` responses) and **timeouts** all lead to the same fallback:
  - return the **most recent stored fact** for this user + movie, of any age
    (`source: "fallback"`, and the UI says it's a previous fact);
  - otherwise return a friendly message: *"Couldn't generate a fun fact right
    now. Please try again in a moment."*
- **Timeouts:** 20 s per request and 1 retry in the SDK, plus a 25 s overall
  deadline (`AbortSignal.timeout`) that also covers the stream.
- **Mid-stream failures:** the partial text is never stored, and the
  server-chosen fallback replaces it in the UI. Truncated output
  (`incomplete`) counts as a failure for the same reason.
- **Internal details stay in the server log:** errors are logged as
  `[facts] generation failed: …` and never sent to the client.

### Safe OpenAI integration

- The API key is used only on the server: `server-only` modules, never
  `NEXT_PUBLIC_`.
- The movie title is user input. It's sent JSON-quoted as data, and the
  instructions tell the model to ignore instructions inside it.
- Generation runs only on `POST` with a valid session and a completed
  onboarding:
  - prefetches, crawlers and cached `GET`s can't spend money;
  - the `SameSite=Lax` session cookie blocks cross-site triggering.
- Output is capped (`max_output_tokens`) and rendered as text, never as HTML.

### 4. Tests

`npm test` runs 20 tests against a **real Postgres test database**, because
the guard's correctness depends on Postgres locking, which a mocked database
can't prove. OpenAI is replaced with a deterministic fake.

- **Cache window** (`test/fact-cache.test.ts`):
  - a 59 s old fact is served and OpenAI isn't called
  - a 61 s old fact triggers generate → store → return
  - the cache is per movie
  - a second request within the window gets the first request's fact
  - new facts are stored with the correct time (time zone regression)
- **Concurrency:**
  - 5 parallel requests → **1** OpenAI call, **1** row, the same fact for
    all 5, and the lease is released
  - a request waits for an in-progress generation
  - if that generation fails, the waiting request falls back
  - an abandoned lease is reclaimed
  - a client disconnect stores nothing and releases the lease
- **Failure:**
  - an OpenAI error returns the newest stored fact
  - a timeout with nothing stored returns the friendly error
  - a mid-stream failure falls back and stores nothing
- **Authorization** (`test/fact-authorization.test.ts`, through the real
  route handler):
  - 401 when signed out, 409 when not onboarded
  - a `userId` smuggled into the query string or body is ignored
  - another user's **fresh** fact for the same movie is never served
  - another user's fact is never used as a fallback
  - one user's lease doesn't block another

The tests were also run against deliberately broken versions of the code.
Removing the guard, shortening the window to 30 s, or dropping the `user_id`
filter each made the relevant tests fail.

The test database is created and migrated automatically. Tests truncate its
tables, so the setup refuses any database whose name doesn't end in `_test`.

## Limitations and possible next steps

- **JWT sessions** can't be revoked server-side ("log out everywhere"). A
  `session_version` column on `users`, checked on each request, would add that.
- **Waiting requests poll** the database (every 400 ms, for at most 45 s).
  At larger scale, Postgres `LISTEN/NOTIFY` or a pub/sub channel would push
  the result instead.
- **One fact per 60 s window applies per user.** If the favorite movie could
  change, the cache would still be correct (it matches on movie), but the
  lease would briefly block generation for the new movie while an old one
  finished.
- **LLM facts can be wrong.** A small model at low reasoning effort is fast
  and cheap but sometimes invents trivia. Use a larger `OPENAI_MODEL` if
  accuracy matters more than latency.

## What I'd improve with 2 more hours

1. **CI.** Add a GitHub Actions workflow that runs lint, type-check and
   `npm test` against a Postgres service container on every pull request.
2. **Per-user cost cap.** The 60 s cache stops bursts, but someone could still
   click once a minute indefinitely. I'd add a limit on new generations per
   hour. It's one indexed count query on `movie_facts`, and the user would get
   their latest fact once they hit it.
3. **Fewer repeated facts.** Send the user's last few facts in the prompt so
   the model picks a different angle each time.
4. **End-to-end tests.** Add Playwright tests for sign-in → onboarding →
   dashboard, with OpenAI mocked, to cover redirects and the streaming UI.
   Backend tests don't reach these.
5. **Observability.** Log cache hit rate, OpenAI latency, and how often the
   fallback is used, so the 60 s window and the timeouts can be tuned from
   real data.

  deliberately broken code to confirm the tests catch bugs.

  were shifted 5 hours by the database time zone, and an output-token limit
  cut off some answers. Both are fixed, and the time zone bug has a regression
  test.
